### 2.2. Ответственность компонентов

**Общий код** отвечает за конфигурации, пути, seed, manifests, описание запуска, атомарное сохранение, проверку происхождения артефактов и сборку отчётов.

**Модули практик** содержат подготовку конкретных данных, модели, обучение, инференс и предметные метрики. Не создавать универсальный класс обучения, принуждающий GAN, Ultralytics и LSTM использовать одинаковый цикл.

**Ноутбуки** являются последовательным, объяснённым интерфейсом к тем же модулям. Не дублировать в них независимую реализацию обучения или расчёта метрик.

**Конфигурации** задают научно значимые параметры. В коде остаются алгоритмы и проверяемые значения по умолчанию.

**Отчёты** формируются из выбранных запусков и сохранённых результатов. Вручную пишутся объяснения, выводы и атрибуция; численные таблицы строятся программно.

Сервисы, базы данных, веб-интерфейс, MLflow, распределённое обучение и контейнеризация не нужны.

Лицензии, не подтверждённые ТЗ, проверяются перед передачей исходных архивов. При неясных условиях в комплект передаются инструкции получения и manifests, а не сам архив.

### 3.2. Общий manifest

Формат — UTF-8 JSONL, один объект на запись. Обязательные общие поля:

```json
{
  "schema_version": 1,
  "sample_id": "stable-source-record-id",
  "split": "train",
  "source_relpath": "relative/path",
  "source_record_id": "record-within-source",
  "content_sha256": "...",
  "group_id": null,
  "status": "included"
}
```

Дополнительные поля:

- Изображения: `width`, `height`, `channels`.
- Классификация: `class_id`.
- Детекция: `image_id`, `annotation_relpath`, `annotation_sha256`.
- CIFAR: `official_split`, `official_index`, `class_id`.
- Ряд: отдельный manifest окон с временными индексами, описанный в §6.

`sample_id` не зависит от абсолютного пути компьютера. Один и тот же исходный объект имеет одинаковый идентификатор во всех экспериментах.

В `dataset.json` сохранять источник, лицензию, проверки, фактическую статистику, правила разбиения и `dataset_id`. Последний вычислять из канонического содержания manifests, mapping, параметров обработки и контрольных сумм источников.

Абсолютное расположение `DATA_ROOT` не должно менять `dataset_id`.

### 3.3. Проверки и исключения

Для изображений:

1. Проверить декодирование, положительные размеры, формат каналов.
2. Нормализовать ориентацию при наличии EXIF, затем преобразовать в RGB.
3. Для проверки точных дубликатов вычислить также hash декодированных RGB-пикселей с учётом размеров.
4. Повреждённые записи исключать из производного manifest с причиной; исходные файлы сохранять.
5. Проверить межвыборочные совпадения пикселей и известные группы происхождения.
6. Для П2 дополнительно проверить разметку и визуальное совмещение рамок.

Формат исключений — `excluded.jsonl`: `sample_id`, причина, результат проверки, затронутый split.

Не считать отсутствие исходных идентификаторов видеосерий доказательством независимости кадров. Для визуально связанных изображений П2 сформировать список подозрительных пар для проверки до обучения.

**Обработка найденной утечки:** подготовка не выдаёт статус `ready`. Сначала сохранить описание конфликта и новую ревизию разбиения. Точные копии с согласованными аннотациями сохранять в одной выборке; при выборе между существующими split приоритет `test > val > train`, остальные копии исключать. Конфликт классов или аннотаций требует разрешения до обучения. Изменение опубликованного split обязательно раскрывать в отчёте.

Известную группу связанных кадров нельзя распределять между выборками. При необходимости пересобрать её размещение до первого полного запуска и применить одинаковый manifest ко всем сравниваемым моделям.

## 4. Практика №1: CNN

Основание: ТЗ §4, P1-01–05.

### 4.1. Данные и вход

Сохранить готовые train/validation/test после проверок §3. Фактические количества считать из архива; не подгонять под ориентировочные проценты ТЗ.

Общий вход обеих моделей: `float32 [B,3,224,224]`. Target: `int64 [B]`, значения `0…14`.

Преобразования `[И]`:

- Train: RGB, resize 224×224, случайное горизонтальное отражение с вероятностью 0.5.
- Val/test: RGB и детерминированный resize 224×224.
- Resize: bilinear с antialias; параметры и версии сохраняются.
- Для обеих моделей — масштабирование в `[0,1]`, затем ImageNet mean `(0.485,0.456,0.406)` и std `(0.229,0.224,0.225)`.

Использование одинаковой нормализации упрощает сравнение. Это фиксированные константы, а не статистика, оценённая на val/test.

### 4.2. Архитектуры

**Собственная CNN [И]:**

```text
[B,3,224,224]
Conv2d(3,32,3,padding=1) → ReLU → MaxPool2d(2)
Conv2d(32,64,3,padding=1) → ReLU → MaxPool2d(2)
Conv2d(64,128,3,padding=1) → ReLU → MaxPool2d(2)
AdaptiveAvgPool2d(1) → Flatten → Dropout(0.2)
Linear(128,15)
[B,15] logits
```

Инициализация Conv/Linear — Kaiming для скрытых слоёв, bias=0; выходной Linear — Xavier. Все параметры обучаемы.

**ResNet18 [И]:**

- `torchvision.models.resnet18`, веса `ResNet18_Weights.IMAGENET1K_V1`.
- Заменить `fc` на `Linear(512,15)`.
- Этап A: обучать только `fc`; backbone, включая BatchNorm, держать в eval.
- Этап B: разморозить `layer4` и `fc`; остальные слои заморожены.
- Статистики всех BatchNorm остаются фиксированными и на этапе B. Вызов общего `model.train()` не должен отменять это правило.

Сохранить полное описание архитектуры и реально вычисленное число всех/обучаемых параметров.

### 4.3. Эксперименты

Loss — `CrossEntropyLoss` по logits; softmax применяется только для предсказаний.

| Опыт | Конфигурация `[И]` |
|---|---|
| `p1_cnn_a` | Adam, LR=1e-3, weight_decay=1e-4 |
| `p1_cnn_b` | То же, LR=3e-4 |
| `p1_resnet_a` | Adam: этап A LR=1e-3; этап B backbone=1e-4, head=1e-3 |
| `p1_resnet_b` | То же; этап B backbone=3e-5, head=3e-4 |

Стартовый batch=32, seed=42; окончательный batch определяется §9. Scheduler не используется, чтобы ограничить число изменяемых факторов.

Для ResNet на этап A выделить `max(1, floor(0.2E))` эпох из согласованного общего лимита `E`; остальные — этап B. Этап B начинается с лучшего checkpoint этапа A; оптимизатор создаётся заново для нового набора параметров.

Выбор — максимальная val accuracy, затем минимальный val loss, затем более ранняя эпоха. Выбрать одну конфигурацию на семейство. На test оценить обе выбранные модели, без дополнительного переобучения.

### 4.4. Результаты

Сохранять:

- Train/val loss и accuracy по эпохам.
- Accuracy, macro-F1, per-class precision/recall/F1 на val/test.
- Матрицы ошибок с одинаковым порядком классов.
- Таблицу всех четырёх опытов с выбранными checkpoint.
- Предсказания test: `sample_id`, `y_true`, `y_pred`, массив вероятностей, `run_id`, `checkpoint_sha256`.
- Примеры верных предсказаний и ошибок. Ошибки выбирать воспроизводимо по убыванию confidence неверного класса, а не только по визуальной выразительности.

При отсутствии ошибок выбранного типа указать это по результатам оценки.

Три ответа П1 оформить отдельными подразделами: архитектура ResNet18; её работа и параметры; CNN против MLP.

## 5. Практика №2: детекция

Основание: ТЗ §5, P2-01–07.

### 5.1. Геометрия и аннотации

Внешний формат YOLO:

```text
class_id x_center y_center width height
```

Координаты нормализованы относительно исходного изображения. Внутренний формат — float32 `xyxy` в пикселях исходного RGB-изображения, без соглашения «+1 пиксель» для площадей:

```text
x1 = (xc - w/2) * W
y1 = (yc - h/2) * H
x2 = (xc + w/2) * W
y2 = (yc + h/2) * H
```

Проверять конечность, целочисленность `class_id`, положительную площадь и нахождение в границах. Отклонения в пределах `1e-6` нормализованных единиц считать округлением и обрезать с записью коррекции. Более крупные ошибки не исправлять молча.

Пустой существующий `.txt` допустим для подтверждённого кадра без объектов. Отсутствующий файл аннотаций не приравнивается автоматически к пустой разметке.

### 5.2. Вход детекторов

Общий размер — 640×640 после letterbox `[И]`. Увеличивать/уменьшать изображение пропорционально; padding RGB `(114,114,114)`.

Сохранять фактические `scale_x`, `scale_y`, `pad_left`, `pad_top` после округления размеров. Обратное преобразование предсказаний:

```text
x_original = (x_letterbox - pad_left) / scale_x
y_original = (y_letterbox - pad_top) / scale_y
```

YOLO использует библиотечный letterbox; адаптер Faster R-CNN реализует то же правило и проходит геометрический тест. Финальный экспорт обоих адаптеров — координаты исходного изображения.

Faster R-CNN принимает список тензоров `[3,640,640]` в `[0,1]`. Его внутренняя нормализация выполняется один раз; внешнюю ImageNet-нормализацию не добавлять. Внутренний resize настроить на 640, исключив повторное изменение масштаба.

### 5.3. Модели

**YOLO26n [И]:**

- Начальные веса `yolo26n.pt`; сохранить URL, hash, версию Ultralytics и конфигурацию архитектуры.
- Дообучать все слои на реальных классах.
- Использовать штатную loss установленной версии, включая обе обучаемые головы. Сохранить resolved training args и названия фактических компонентов loss.
- Не добавлять вручную DFL-компонент по аналогии с другой YOLO.

Явно выбрать **one-to-many с NMS**, `nms=True`, одинаково при валидации обучения и итоговом инференсе. В текущей документации YOLO26 выбор головы влияет на предсказания; полагаться на незафиксированный default нельзя. [Документация Ultralytics](https://docs.ultralytics.com/guides/end2end-detection).

**Faster R-CNN [И]:**

- `fasterrcnn_resnet50_fpn_v2`.
- Начальные веса `FasterRCNN_ResNet50_FPN_V2_Weights.COCO_V1`.
- Сначала загрузить предобученную модель, затем заменить `roi_heads.box_predictor` на `FastRCNNPredictor(in_features,8)`.
- `trainable_backbone_layers=3`; обучать доступные поздние блоки backbone, FPN, RPN и ROI heads.
- Статистики BatchNorm фиксировать при обучении.
- Loss — сумма возвращаемых моделью classification, box regression, objectness и RPN regression losses.

Число классов torchvision включает background; официальные веса принимают изображения в `[0,1]`. [Документация torchvision](https://docs.pytorch.org/vision/0.26/models/generated/torchvision.models.detection.fasterrcnn_resnet50_fpn_v2.html).

### 5.4. Матрица обучения

| Опыт | Настройки `[И]` |
|---|---|
| `p2_yolo_a` | AdamW, lr0=1e-3, weight_decay=5e-4 |
| `p2_yolo_b` | То же, lr0=3e-4 |
| `p2_frcnn_a` | SGD, LR=5e-3, momentum=0.9, weight_decay=5e-4 |

Стартовый batch: YOLO=8, Faster R-CNN=2. Финальные значения фиксировать после smoke.

Аугментации — горизонтальное отражение с вероятностью 0.5 только на train. Для YOLO явно отключить mosaic, mixup, cutmix, copy-paste, HSV, вращение, сдвиг, масштабирование, shear и perspective. Это ограничивает различия предобработки при сравнении. Сохранять итоговый resolved config, чтобы изменения библиотечных defaults не включили скрытые преобразования.

Для YOLO установить фиксированный LR: отключить warmup и снижение LR соответствующими параметрами закреплённой версии. Для Faster R-CNN scheduler отсутствует. В baseline precision — FP32.

Штатное накопление градиентов YOLO не должно оставаться неявным: настроить номинальный batch равным фактическому и проверить accumulation=1. Различие batch и оптимизаторов между детекторами раскрыть в отчёте.

### 5.5. Общая оценка

Сохранять полный набор предсказаний при confidence≥0.001, class-aware NMS IoU=0.7, максимум 100 detections на изображение. У Faster R-CNN задать соответствующие пороги ROI heads; внутренний RPN NMS остаётся частью архитектуры и документируется.

Общий evaluator — `pycocotools.COCOeval`, тип `bbox`:

- IoU: 0.50…0.95 с шагом 0.05.
- Recall: 0…1 с шагом 0.01.
- `maxDets=[1,10,100]`.
- Все целевые классы, без background.
- Основные метрики: AP50 и AP50–95 по области `all`.
- Классы без GT в split показывать как неопределённые; не усреднять служебное `-1` как результат.

Параметры соответствуют стандартному COCO evaluator. [Исходный код COCOeval](https://raw.githubusercontent.com/cocodataset/cocoapi/master/PythonAPI/pycocotools/cocoeval.py).

Precision/Recall для общей таблицы считать отдельно при **confidence=0.25, IoU=0.50**: matching внутри изображения и класса, предсказания по убыванию score, каждый GT сопоставляется не более одного раза. Основное усреднение — micro по TP/FP/FN; дополнительно per-class. Не смешивать эти числа со штатным выбором confidence в Ultralytics.

COCO GT содержит `images`, `annotations`, `categories`; bbox — `[x,y,width,height]` в исходных пикселях, `area=width*height`, `iscrowd=0`. Список изображений включает также кадры без объектов и без предсказаний.

**Выбор checkpoint:** максимальный общий val AP50–95, затем AP50, затем более ранняя эпоха. Общую оценку выполнять после каждой эпохи. Штатный `best.pt` YOLO не считать автоматически выбранным проектом checkpoint, если критерий библиотеки отличается.

На test оценивать по одному выбранному checkpoint каждого детектора. Штатные YOLO val/test-метрики сохранять отдельно: `box.map50` — AP50, `box.map` — AP50–95.

### 5.6. Loss, примеры и экспорт

Для YOLO сохранять штатные train/val-компоненты loss. Для Faster R-CNN валидировать loss отдельным проходом без градиентов в режиме, возвращающем losses: BatchNorm остаётся eval, RNG временно фиксируется и затем восстанавливается. Проверять неизменность параметров и buffers. Инференс метрик выполняется обычным `eval()`.

Абсолютные loss разных архитектур не сравнивать как одну шкалу качества.

Обязательные артефакты:

- Общая таблица двух детекторов на val/test.
- Per-class AP/P/R, PR-кривые.
- Train/val loss и val AP по эпохам.
- JSONL предсказаний в исходных координатах и COCO JSON.
- FP/FN и правильные detections с указанием порогов.
- Новые внешние изображения, отсутствующие во всех split, с источником и hash.

Для новых изображений инженерный минимум — три доступных изображения подходящих классов. Если их нет, test-демонстрацию сохранить отдельно, а внешнюю демонстрацию отметить незавершённой. Без GT новых изображений mAP не рассчитывать.

## 6. Практика №3: LSTM

Основание: ТЗ §6, P3-01–04; временной ряд — допущение `[А]`.

### 6.1. Временная ось

Использовать только `Date Time` и `T (degC)`. Время разбирать по формату исходного CSV; не присваивать неподтверждённый часовой пояс.

Порядок обработки `[И]`:

1. Проверить даты и числовые значения температуры.
2. Отсортировать наблюдения по времени.
3. Точные дубли одной временной записи удалить с журналом.
4. Конфликтующие значения одной временной метки считать дефектом данных и исключить эту метку.
5. Сформировать завершённые часовые интервалы `(t−1h,t]`, метка — правая граница `t`.
6. Часовое значение — среднее шести ожидаемых десятиминутных измерений. Неполный час оставить пропуском.
7. Интерполяцию и заполнение будущими значениями не применять.

Не удалять значения только потому, что они редкие или отрицательные. Конечные экстремумы сохранять; подозрительные исходные значения показать в аудите.

Разбиение проводить по полной регулярной часовой сетке до исключения окон:

```text
n_train = floor(0.70 * N)
n_val   = floor(0.15 * N)
train = [0, n_train)
val   = [n_train, n_train+n_val)
test  = [n_train+n_val, N)
```

Сохранить точные временные границы.

### 6.2. Окна и нормализация

Для split `[a,b)` и `i=a+48,…,b−1`:

```text
X_i = [T_(i−48), …, T_(i−1)]
y_i = T_i
```

Окно включать только при наличии всех 49 значений. Ни один вход или target не пересекает границу split.

`StandardScaler`: mean/std по конечным значениям train; `ddof=0`. Если std=0, подготовка завершается ошибкой. Сохранить параметры в JSON вместе с именем признака и диапазоном fit.

Manifest окон:

```text
window_id, split, input_start, input_end, target_time,
input_start_index, target_index, included, exclusion_reason
```

Вход LSTM — `[B,48,1]`, выход — `[B,1]`, target — `[B,1]`.

### 6.3. Модель и опыты

Однослойная однонаправленная `LSTM(batch_first=True)`; использовать выход последнего timestep и линейную голову `hidden_size → 1`. Состояния hidden/cell обнулять для каждого независимого окна.

| Опыт | Настройки `[И]` |
|---|---|
| `p3_lstm_a` | hidden_size=64 |
| `p3_lstm_b` | hidden_size=128 |

Общее: MSE по нормализованной цели, Adam LR=1e-3, weight_decay=0, batch=64, gradient clipping по норме 1.0, seed=42. Scheduler и dropout отсутствуют.

Shuffle допустим только для готовых train-окон; последовательность внутри окна неизменна. Val/test не перемешивать.

Выбор — минимальный val RMSE в °C, затем val MAE, затем более ранняя эпоха.

### 6.4. Инференс и результаты

Режим — одношаговый скользящий прогноз. Для прогноза следующего часа используются последние 48 уже наблюдённых часовых значений. Предсказание не подставляется вместо истинного наблюдения в следующее окно.

Наивный baseline: `y_pred=T_(i−1)` на точно тех же окнах. Он не обучается.

Метрики train/val/test в режиме eval: MAE, RMSE, R² после обратного преобразования в °C. При постоянной целевой выборке R² записывать `null` с причиной.

Сохранить:

- `predictions.csv`: `window_id,timestamp,y_true,y_pred,split,run_id`.
- Аналогичный файл baseline.
- Train/val loss и MAE/RMSE/R² по эпохам.
- График всего test и увеличенный фрагмент первых 168 доступных test-прогнозов.
- Таблицу крупнейших абсолютных ошибок и их временной контекст.
- Сравнение LSTM и baseline на одинаковом наборе timestamp.

Нельзя подписывать этот эксперимент как рекурсивный многосуточный прогноз.

## 7. Практика №4: GAN

Основание: ТЗ §7, P4-01–04.

### 7.1. Разбиение и вход

Из официального train CIFAR-10 выделить development стратифицированно: по 1000 объектов каждого класса с seed=42; остальные — train. Официальный test оставить для финальной оценки.

До обработки дефектов ожидаются 40 000/10 000/10 000. Фактические количества определяются подготовкой.

Train-вход — `[B,3,32,32]`, преобразование `x/127.5−1`. Аугментаций нет. Метки нужны для аудита распределения, но не подаются в unconditional GAN.

Межвыборочные дубликаты разрешать до обучения. Если очистка уменьшает независимый финальный reference ниже 10 000 изображений, P4-03 остаётся заблокированным до пересмотра разбиения; нельзя добирать объём повторением картинок.

### 7.2. Архитектуры `[И]`

**Vanilla GAN**

```text
G:
z [B,100]
Linear 100→256 → ReLU
Linear 256→512 → ReLU
Linear 512→1024 → ReLU
Linear 1024→3072 → Tanh
reshape [B,3,32,32]

D:
Flatten 3072
Linear 3072→1024 → LeakyReLU(0.2)
Linear 1024→512 → LeakyReLU(0.2)
Linear 512→256 → LeakyReLU(0.2)
Linear 256→1
```

**DCGAN**

```text
G:
z [B,100,1,1]
ConvTranspose 100→256, k4/s1/p0 → BN → ReLU      # 4×4
ConvTranspose 256→128, k4/s2/p1 → BN → ReLU      # 8×8
ConvTranspose 128→64,  k4/s2/p1 → BN → ReLU      # 16×16
ConvTranspose 64→3,    k4/s2/p1 → Tanh           # 32×32

D:
Conv 3→64,    k4/s2/p1 → LeakyReLU(0.2)         # 16×16
Conv 64→128,  k4/s2/p1 → BN → LeakyReLU(0.2)    # 8×8
Conv 128→256, k4/s2/p1 → BN → LeakyReLU(0.2)    # 4×4
Conv 256→1,   k4/s1/p0                           # 1×1
reshape [B,1]
```

У D нет sigmoid. Conv перед BN — без bias. Инициализация DCGAN: веса Conv из `N(0,0.02)`, BN weight из `N(1,0.02)`, bias=0. Linear Vanilla — Xavier, bias=0.

### 7.3. Обновление G/D

Один training step содержит одно обновление D и одно G:

1. Очистить градиенты D.
2. Сэмплировать `z_D ~ N(0,I)`.
3. Получить fake без графа G; при этом G держать в eval, чтобы шаг D не обновлял BN генератора.
4. D в train вычисляет real и detached fake.
5. `loss_D = 0.5 × (BCEWithLogits(D(real),1) + BCEWithLogits(D(fake),0))`.
6. Backward и optimizer D step.
7. Очистить градиенты G; временно отключить градиенты параметров D и перевести D в eval, зафиксировав BN.
8. G в train генерирует из нового `z_G`.
9. `loss_G = BCEWithLogits(D(G(z_G)),1)`.
10. Backward проходит через D ко входу G; выполнить optimizer G step.
11. Восстановить D train и `requires_grad`.

Это выбранный порядок управления BN и градиентами. Он должен быть одинаково реализован и проверен, а не зависеть от порядка вызовов `train()`.

Оба оптимизатора — Adam, LR=2e-4, betas=(0.5,0.999), weight_decay=0. Стартовый batch=64, FP32, seed=42. Для DCGAN batch должен быть не меньше 2; train использует `drop_last=True`.

Обе архитектуры получают одинаковый фактический batch и запланированное число D/G-обновлений. Если авария нарушила равенство, это указывается в сравнении.

### 7.4. Выбор checkpoint и динамика

GAN loss не используется как критерий лучшего генератора.

До запуска зафиксировать:

- 64 визуализационных latent-вектора, seed=4240.
- Development latent-векторы, seed=4242.
- Финальные latent-векторы, seed=4243.

Сами массивы сохранять; генерация батчами читает их последовательно.

Чтобы ограничить стоимость выбора `[И]`:

- Выделить фиксированные 2000 development real, стратифицированно из development.
- Выполнять development FID на 2000 fake в не более чем пяти равномерно расположенных контрольных точках полного бюджета, включая последнюю.
- Подписывать эту метрику `fid_dev_2000`, не выдавать её за финальный FID.
- Выбирать минимальное конечное `fid_dev_2000`; при равенстве — более ранний checkpoint.
- Визуальную оценку дефектов и разнообразия сохранять рядом. Она объясняет ограничения выбранной модели и не служит скрытым способом ручного перебора test.

Полноценную финальную оценку проводить только для выбранного G каждой архитектуры.

### 7.5. Финальные FID/IS

`[П]` Минимум 10 000 real и 10 000 fake на каждую модель.

Протокол `[И]`:

1. Real — независимая финальная выборка CIFAR-10; порядок определяется manifest.
2. Fake — 10 000 новых latent-векторов из сохранённого массива final, одинакового для сравнения двух архитектур.
3. G находится в eval; градиенты отключены.
4. Fake преобразуется в RGB uint8: `round(clamp((x+1)/2,0,1)*255)`.
5. Сохранить каждое изображение отдельным PNG 32×32 без потерь, плюс индекс и hash. Не использовать сетки и JPEG для метрик.
6. Real передавать как исходные RGB uint8.
7. `torch-fidelity`: `input1=fake`, `input2=real`, `fid=True`, `isc=True`, `kid=False`, `prc=False`.
8. Extractor — `inception-v3-compat`; FID feature=`2048`; IS feature=`logits_unbiased`.
9. `isc_splits=10`, `samples_shuffle=True`, `rng_seed=4243`.
10. Внутренний dtype extractor — float32; AMP отключён.
11. IS рассчитывается по fake, выводятся mean и std десяти splits, а не доверительный интервал.
12. Сохранять версию evaluator, hash его весов, порядок данных, все параметры и raw output.

Extractor самостоятельно приводит uint8-вход к 299×299 совместимой с TensorFlow bilinear-интерполяцией и нормализует его; внешний resize и ImageNet-нормализация не добавляются. [Код extractor](https://raw.githubusercontent.com/toshas/torch-fidelity/master/torch_fidelity/feature_extractor_inceptionv3.py). Параметры splits, shuffle и RNG задаются явно. [Параметры torch-fidelity](https://raw.githubusercontent.com/toshas/torch-fidelity/master/torch_fidelity/defaults.py).

Точную версию пакета закрепить при подготовке среды и проверить перечисленные параметры по установленной версии. Страницы `latest` и ветка `master` служат основанием выбора интерфейса, но не заменяют version lock.

Не удалять похожие сэмплы генератора для улучшения метрик. Различать естественные повторы из-за коллапса и искусственное копирование файлов ради числа 10 000; последнее запрещено.

### 7.6. Иллюстрации

Сохранять:

- Реальные примеры и распределение классов.
- Loss G/D по эпохам и шагам.
- Сетки 8×8 на фиксированных z в контрольных точках.
- Финальную сетку на свежем шуме.
- Линейную интерполяцию для восьми пар latent-векторов, по восемь точек `α∈[0,1]`, включая края.
- Таблицу архитектур, параметров, фактических обновлений, development FID и финальных FID/IS.
- Анализ артефактов, повторов, стабильности и ограничений метрик.

Наличие плохого качества не разрешает подменять результаты. Проверяемый корректный эксперимент и содержательные ограничения фиксируются независимо от величины FID.

| `verify(selection)` | Комплект артефактов | Машиночитаемый результат проверок |

GAN evaluation дополнительно принимает каталоги real/fake и protocol.

Ошибки CLI:

- `2` — неверная конфигурация или неподдерживаемая комбинация.
- `3` — отсутствующие/непрошедшие проверку данные или веса.
- `4` — недоступное устройство или неподтверждённый полный бюджет.
- `5` — ошибка обучения/оценки.
- `6` — неполный комплект для финального отчёта.

Успешное завершение smoke не означает успешное завершение `verify` полного проекта.

### 9.1. Среда

Базовый стек `[И]`: Python 3.11, PyTorch/torchvision, NumPy, pandas, scikit-learn, Pillow, Matplotlib, PyYAML, Jupyter/nbclient. П2 добавляет Ultralytics и pycocotools; П4 — torch-fidelity; отчёты — ReportLab.

Сохранять для каждого запуска:

- Python, ОС и архитектуру.
- Полный список пакетов с версиями.
- Версии torch/torchvision, CUDA runtime и драйвера.
- Название GPU, VRAM, precision.
- Hash исходного кода; commit при наличии Git.

`requirements.txt` каждой практики содержит закреплённые реально использованные зависимости. Способ установки PyTorch под выбранный backend описывается отдельно в README.

`device=auto`: CUDA при доступности, иначе CPU. MPS не включается автоматически: его поддержка конкретными операциями не проверена. Для П1 full при CPU — явная блокировка P1-05; smoke и оценка сохранённых весов на CPU допустимы.

### 9.2. Smoke и определение бюджета

Smoke для каждой архитектуры `[И]`:

1. Проверка forward/loss/backward.
2. Прогрев до пяти шагов.
3. До двадцати измеряемых training steps.
4. Небольшой validation pass.
5. Сохранение и загрузка checkpoint в новом процессе.
6. Один шаг продолжения и проверка предсказаний.

Для GAN полный FID в smoke не нужен: проверяются форматы и малый вызов evaluator с явной маркировкой диагностической метрики.

При OOM уменьшать batch вдвое до допустимого минимума; найденное значение сохранить в smoke-результате. Для П4 выбрать минимальный устойчивый batch из двух архитектур, чтобы полные опыты использовали одинаковый batch.

`budget.yaml` после smoke должен содержать:

```yaml
schema_version: 1
status: unresolved
device: null
practice_time_limit_seconds: null
planned_epochs: null
batch_size_by_model: {}
measured_step_seconds_by_model: {}
estimated_evaluation_seconds: null
basis_smoke_run_ids: []
```

Статус `unresolved` разрешает подготовку и smoke, но запрещает full train.

После определения доступного времени:

- Измерить стоимость train и validation на выбранном оборудовании.
- Учесть все опыты практики и стоимость финальной оценки.
- Оставить инженерный резерв 20% времени.
- Рассчитать единый предел эпох сравниваемых конфигураций как целую часть доступного времени, делённого на суммарную оценочную стоимость эпох.
- Для П1 обеспечить возможность обеих стадий ResNet.
- Для П4 учесть development FID и финальную оценку обеих GAN, назначить одинаковое число обновлений.
- Сохранить расчёт, фактическое устройство и окончательные значения до full train.

Если лимит не позволяет выполнить осмысленный полный цикл, не объявлять вычисленный короткий запуск полноценным. Зафиксировать ресурсное ограничение и конкретно недостающие этапы.

### 9.3. Остановка и возобновление

Для П1–П3 ранняя остановка `[И]`: отсутствие улучшения основной val-метрики в течение `max(3, ceil(0.2E))` проверок. Для ResNet счётчик перезапускается при переходе к fine-tuning; стадия A не отменяет стадию B. Если бюджет исчерпан раньше patience, остановка по бюджету.

Для GAN ранняя остановка по loss не применяется. Завершение — согласованный бюджет либо техническая ошибка.

Во всех работах:

- Неконечные loss/градиенты → остановка с диагностикой.
- Внешнее прерывание → сохранить доступное корректное состояние; частичный шаг не считать завершённым.
- OOM полного опыта → статус interrupted/failed. Изменение batch создаёт новую конфигурацию и новый `run_id`, а не скрытую правку старого опыта.
- Resume с теми же параметрами продолжает прежний run.
- Изменение данных, модели или научно значимых параметров — новый run с `parent_run_id`.

Точное продолжение гарантируется только с поддерживаемой границы checkpoint и в закреплённом окружении; побитовое равенство разных GPU не обещается.

## 10. Артефакты и происхождение результатов

### 10.1. Структура запуска

```text
artifacts/
  dataset/
  runs/
    RUN_ID/
      config.resolved.yaml
      run.json
      environment.json
      history.csv
      events.jsonl
      checkpoints/
      predictions/
      metrics/
      figures/
      samples/
  selection.json
  report_bundle.json
```

`run_id`: UTC timestamp + experiment_id + короткий hash конфигурации. Проверять уникальность.

`run.json` содержит режим `smoke/full`, dataset_id, hashes конфигурации/кода, источник весов, фактический бюджет, родительский run, timestamps и причину завершения.

Состояния:

```text
created → running → trained → evaluated → verified
                   ↘ interrupted / failed
```

`verified` отдельного запуска не означает завершение всей практики.

### 10.2. Checkpoint

Обязательные поля собственного checkpoint:

- `schema_version`, `run_id`, architecture config.
- `model_state_dict`.
- Optimizer и scheduler state, если scheduler применяется.
- AMP scaler state, если используется.
- Завершённая эпоха, global step, текущая стадия.
- Лучшая val-метрика и состояние early stopping.
- Python/NumPy/torch CPU/CUDA RNG.
- Состояние генератора DataLoader.
- Dataset/config/mapping/preprocessing hashes.

Для GAN — G, D и оба оптимизатора; визуализационные z доступны по проверяемой ссылке.

Сохранять `last` для продолжения и `best` для оценки. Запись — временный файл в той же файловой системе и атомарная замена.

Для Ultralytics сохранять native checkpoint и sidecar метаданных/RNG. Для resume нужен **неочищенный checkpoint с состоянием оптимизатора**, сохранённый до возможного удаления training state библиотекой. Загрузка одних inference-весов не считается восстановлением обучения.

### 10.3. Логи и метрики

`history.csv`: длинный формат:

```text
run_id,epoch,step,split,metric,value,unit,elapsed_seconds
```

Loss усреднять с корректным весом по числу объектов, а не простым средним неодинаковых батчей.

`metrics/*.json`:

```json
{
  "schema_version": 1,
  "run_id": "...",
  "checkpoint_sha256": "...",
  "dataset_id": "...",
  "split": "test",
  "protocol_id": "...",
  "sample_count": 0,
  "values": {},
  "undefined": {}
}
```

Пример показывает структуру; `sample_count` и `values` заполняются только фактическими результатами. Неопределённые метрики — `null` с причиной, не нули-заглушки.

`selection.json` перечисляет выбранные checkpoints по семействам, criterion, val-результаты и статус опытов. Test-метрики в выборе не участвуют.

Каждая итоговая таблица и иллюстрация в `report_bundle.json` связана с run, checkpoint, split и источником данных.

## 12. Проверка реализации и приёмка

### 12.1. Проверки до полного обучения

- Корректность manifests и mapping; отсутствие пересечений ID и подтверждённых групп.
- Все ожидаемые классы присутствуют в train.
- Ошибочные изображения/аннотации дают понятные исключения.
- П2: YOLO ↔ xyxy ↔ COCO и letterbox round-trip; допустимая погрешность исходных координат `1e-3` пикселя `[И]`.
- П2: label 0 исходного mapping становится torchvision label 1 и возвращается обратно.
- П3: окно ровно 48 часов; target следующий час; отсутствие выхода за split.
- П3: изменение val/test не меняет fitted scaler.
- П4: диапазон и shapes G/D, отсутствие конечного sigmoid.
- Проверка изменяемых параметров: D-step не меняет G; G-step не меняет D и его BN buffers.
- Проверка train/eval-режимов замороженных слоёв.

### 12.2. Метрики на контролируемых примерах

- П1: идеальные и полностью ошибочные предсказания; правильные macro/per-class показатели.
- П2: идеальная рамка, FP, FN, неправильный класс, повторная detection, пустой кадр, отсутствие predictions.
- П2: идеальные predictions дают AP=1 при подходящем синтетическом наборе.
- П3: нулевая ошибка, известное постоянное смещение, постоянный target и обратное масштабирование.
- П4: одинаковые наборы дают FID, близкий к нулю в численном допуске; диапазон uint8 и число fake проверяются.
- IS для одинакового распределения вероятностей близок к 1; mean/std агрегируются по заданным splits.

Диагностические метрики синтетических и smoke-данных не попадают в финальные таблицы.

### 12.3. Checkpoint и сквозная проверка

Для каждой архитектуры:

1. Smoke-step и сохранение checkpoint.
2. Новый процесс загружает checkpoint.
3. Проверка совпадения inference-выходов на фиксированном входе.
4. Проверка optimizer state, counters и возможности следующего шага.
5. Для поддерживаемого детерминированного CPU-сценария — сравнение непрерывного и восстановленного короткого запуска.

Для готовой практики: повторно оценить выбранные сохранённые веса и сверить результаты с сохранёнными predictions/metrics. Полное повторное обучение не является обязательным тестом.

Метрики из одного и того же файла predictions должны совпадать до округления. При повторном inference на том же закреплённом устройстве использовать технический допуск `atol=1e-6, rtol=1e-5` для float-результатов `[И]`; расхождения классов и matching детекции разбирать отдельно, а не скрывать округлением.

В PDF числа должны совпадать с форматированием исходных метрик. Повторно отображаемые показатели берутся из одной таблицы, а не вычисляются разными ячейками.

| 6. Финальная оценка | Выбранные val/development checkpoints | Реальные test-артефакты, внешняя демонстрация П2, полные FID/IS |
| 7. Документы | Проверенные результаты | Четыре последовательных ноутбука и четыре PDF |
| 8. Передача | Проверка документов | `docs/acceptance.md`, инструкции и доступные артефакты |

Ресурсоёмкие работы выполнять последовательно П1 → П2 → П3 → П4 согласно организационной рекомендации ТЗ. Подготовка архитектур, интерфейсов, синтетических тестов и шаблонов отчётных разделов возможна до определения GPU-бюджета.

Существенные нерешённые вопросы:

1. **П2: обязательны ли YOLO26s и YOLO26m?** Базовая реализация использует YOLO26n и Faster R-CNN; ответ влияет на число обучений и окончательный статус P2-06.
2. **П3: достаточно ли одного домена?** Базовая реализация — временной ряд. Требование текста добавит отдельный датасет, обработку, обучение, метрики и разделы документов.
3. **Какая вычислительная среда и какое время доступны?** Это блокирует фиксацию полного бюджета, но не подготовку кода и smoke-тестов. Оценка времени производится по измерениям, а не по предположению о GPU.
4. **Требует ли преподаватель Generative Precision/Recall в П4?** Базовый вариант следует допущению ТЗ и ограничивается FID/IS; положительный ответ добавит оценку, но сам по себе не требует повторного обучения GAN.

Доступность архивов и подходящих новых изображений П2 проверяется на этапе подготовки. Если источник недоступен, соответствующая часть получает конкретный блокер; смена датасета не производится скрыто.

После проверки согласованности разделов приняты единые правила: выбор только по val/development, общие mappings и manifests, фиксированные протоколы метрик, отдельные smoke/full-артефакты, воспроизводимая оценка сохранённых весов и генерация документов из фактических результатов.
